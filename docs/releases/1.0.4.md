A central no sino consome avisos publicados pelo ADM. O push é opcional e requer login e autorização do dispositivo. O app Android precisa desta versão para registrar o token nativo. Agendamentos são processados pelo backend; rascunhos e avisos cancelados não aparecem no feed público.

## Configuração

A VAPID dos arquivos `.env.production` e `.env.mobile` é pública. O arquivo `deploy/sqlite-storage.compose.yml` monta `./data` em `/data` para manter os arquivos WAL/SHM do SQLite persistentes no host. A credencial privada FCM deve ficar fora do repositório e da pasta pública, montada somente para leitura pelo arquivo `deploy/notifications.compose.yml`. O backend lê `FIREBASE_SERVICE_ACCOUNT_PATH`.

```sh
docker compose -f docker-compose.yml -f docker-compose.override.yml -f deploy/sqlite-storage.compose.yml -f deploy/notifications.compose.yml up -d
```

Use o fluxo de publicação com backup prévio e imagens verificadas; não execute atualização em produção sem autorização. As migrations SQLite são aditivas. Uma reversão de código não deve restaurar cegamente um banco antigo e descartar atividade posterior dos usuários.

## Validação

29 testes: 8 backend, 7 utilitários reais, 6 navegador/APIs nativas simuladas e 8 Java do atualizador. TypeScript, builds web/mobile, Gradle release, assinatura e alinhamento aprovados. 67 arquivos mobile conferidos no APK, sem divergências ou credenciais privadas. Manifesto final com permissão POST_NOTIFICATIONS e serviço FCM. Nenhuma garantia de entrega real foi inferida das simulações; o teste físico de push fica para o aparelho do usuário.

```sh
cd frontend
npm ci
npx playwright install chromium
npm run test:notifications
```

A validação FCM `validateOnly` retornou HTTP 200 sem enviar alertas. Para testar após instalar: entrar na conta, abrir o sino, ativar notificações, colocar o app em segundo plano e enviar um aviso de teste pelo ADM.
